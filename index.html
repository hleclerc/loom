loomYour C++ kernel, as a function of your framework

Write the inner loop once, in plain C++ or CUDA. loom compiles it, hands it the arrays of Jax, Torch, NumPy or CuPy, runs it inside jit, vmap and grad, and gives you the gradient you wrote for it.

Two worlds, one boundary

Outside, your users keep their framework: Jax, Torch, NumPy or CuPy arrays in, the same kind out. Inside, every value is a loom tensor, whoever owns its buffer, so your code is written once, clearly, for all of them.

Compiled on demand, or shipped precompiled

The first call compiles and caches. For a wheel, a script of your package fills a catalogue ahead of time, one directory per architecture, so a user with no compiler still gets the kernels.

A kernel that never counts dimensions

Coordinates are read by name: coords[axis], coords + axis, coords.axes - batch_axes. The same body runs in 2-D and in 3-D, batched or not, and a vmap adds an axis without the kernel knowing.

The role is said on the value

loom.out( x ), loom.mutable( x ), loom.scratch( x ): what the kernel reads, writes or only borrows is written where the argument is passed, not in a list on the side that rots.

A kernel, and its gradient, in one screen ​

One explicit step of the heat equation on a grid. The C++ is the whole kernel; the Python is the whole binding.

cpp
struct OneStep {
    HD void operator()( auto coords, auto &&args, auto batch_axes ) const {
        const auto main_axes = coords.axes - batch_axes;     // my axes, not the vmap's

        const TF uc = args.inputs.temperature( coords );
        if ( on_border( coords, main_axes, args ) ) {
            args.outputs.temperature( coords ) = uc;
            return;
        }

        TF total = 0;
        for_each( main_axes, [&]( auto axis ) {              // unrolled at compile time
            total += args.inputs.temperature( coords + axis )
                   + args.inputs.temperature( coords - axis ) - 2 * uc;
        } );
        args.outputs.temperature( coords ) = uc + args.inputs.coef * total;
    }
};
python
import loom

def step( temperature, coef ):
    return loom.ffi_call( "diffusion_step", _forward, _backward,
        temperature = loom.mutable( temperature ),   # read, then rewritten
        coef = coef,
    )

def evolve( temperature, coef, nb_steps ):
    for _ in range( nb_steps ):
        temperature = step( temperature, coef )
    return temperature

temperature is a Jax, Torch, NumPy or CuPy array, as it is, and step returns one of the same kind. There is nothing to wrap, nothing to unwrap, and nothing about 2-D in the kernel. The full walkthrough writes it line by line, adjoint included.

What it is for ​

Everything you would write a custom operator for: a stencil, a geometric query, a rasteriser, a particle interaction, a piece of numerical code you already have in C++ and that your model must now differentiate through. If a few lines of jnp or torch express it, use those. loom starts where the operation is naturally a loop over a structure that tensor primitives do not express, or where the C++ already exists.
